# GPT-6 Astra 向け指示監査

監査日: 2026-09-13。確認した実行ホストは `citrus-vm`。
監査開始時のリポジトリは `db07b37`、作業ツリーと index は空だった。

Eric Provencher の
[Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)
（2026-09-11）を確認した。記事は、スキルの発火条件と説明を絞ること、
必要な手順だけ段階的に読むこと、毎回の一律な事前読み込みを減らすこと、
判断を委ねる範囲と完了条件を明確にすることを勧めている。
[公式のAstraガイド](https://developers.openai.com/api/docs/guides/latest-model)
も、指示の矛盾、過剰な確認、変更規模に見合わない検証の見直しを扱っている。

以下の優先順位と修正案は、これらを現在の構成へ適用した監査判断である。
短縮そのものを目的にせず、実際の誤作動を防ぐ境界は残す。

## 対象と変更範囲

確認対象は、個人スキル8件の全文、ルート `AGENTS.md`、CodexのNix設定と
Home Managerによる配布・上書き処理、関連する運用文書、利用可能なスキルの
説明である。プラグインは特に `figma-swiftui`、`google-docs`、システムの
`openai-docs` を確認した。全プラグインの参照文書・スクリプトまでを検証した
ものではなく、実タスクによるモデル品質・料金の比較実験も行っていない。

今回実装するのは、明示された「Astra / xhighを既定にする」「sub-agentを
使わない」という設定変更とその文書化。下記のその他の改善は提案であり、
`AGENTS.md`、個人スキル本文、プラグインのキャッシュは書き換えていない。

## 優先して改善する箇所

### 1. モデル設定と委譲指示の矛盾を解消する — 今回対応

[システム設定](../hosts/citrus/codex.nix)はAstraを選択していたが、通常・Planの
推論強度と文章の指示は `medium` だった。一方、ユーザー設定にはAstra / xhighが
あり、Home Managerのactivationはユーザーの推論強度を削除するため、再適用時に
mediumへ戻る構成だった。

さらに、独立レビューを委譲例外とする全体指示と、規模の大きい作業を自動で
Lunaへ委譲する [luna-delegation](../skills/luna-delegation/SKILL.md) が併存していた。

通常・Planを `xhigh` に揃え、`features.multi_agent = false` を設定し、
未使用になるLunaの既定値を削除した。全体指示からレビュー時の委譲例外を除き、
別タスクによる代用も禁止した。自動委譲スキルはソースを残して配布から除外する。
Home Managerはモデル・推論強度・multi_agentのユーザー層の上書きを除去する。
既存タスク固有の設定を遡って変更したとは扱わない。

### 2. ホスト名で固定された古い適用条件を修正する — 優先度: 高

[add-nix-mcp](../skills/add-nix-mcp/SKILL.md)の末尾と
[add-nix-skill](../skills/add-nix-skill/SKILL.md)の末尾は、ライブ適用を
`citrus` の場合だけに限定している。しかし
[citrus-vm/default.nix](../hosts/citrus-vm/default.nix)はCitrusをimportする。
ルート `AGENTS.md` の「確認済みローカルホストに影響するなら適用する」という
条件と矛盾し、VM上で必要な適用を省いてしまう可能性がある。

修正案: スキルはホスト名を列挙せず、`AGENTS.md` の影響判定と適用手順へ
リンクし、MCP・スキル固有の確認だけを追加する。
[development.md](development.md)のビルド対象表も、3ホスト構成に合わせる。
リモート操作を許可する変更は不要。

### 3. 全作業共通の読み込み義務を、必要時の参照へ変える — 優先度: 中

[AGENTS.md](../AGENTS.md)の「File names and responsibilities」は、編集前に
READMEの構成図、対象ファイル、関連ファイルとimportを読むことを一律に要求する。
配置原則は有用だが、既知のファイルの小さな修正まで同じ準備は必要ない。

修正案: 「対象の振る舞いと必要な呼び出し元・importを確認する。新しい配置を
決めるときはREADMEの構成図、パッケージ所有権を変えるときはpackage-audit、
適用時はdevelopmentとホストの検証手順を参照する」とする。
同じ実行環境・作業で確認済みのホスト情報や未変更の資料は再利用し、環境が
変わった場合や情報が不確かな場合に確認し直す、と明記するとよい。

### 4. 完了と公開の境界を分ける — 優先度: 高

[codex.nix](../hosts/citrus/codex.nix)の全体指示は、すべてのGit編集で
commitとpushを必須とし、pushできなければ未完了とする。
このリポジトリの [AGENTS.md](../AGENTS.md) はcommitと条件付きのローカル適用を
要求しているが、pushを完了条件にしていない。

pushを毎回自動実行したい意図があるなら、その継続承認は維持できる。
ただし対象リポジトリ・remote・ブランチと、既存の未pushコミットを含めてよいかを
明示した方がよい。監査開始時の `main` は `origin/main` より3コミット先行しており、
今回の変更だけを通常のpushで公開することはできない。

提案する区別は、依頼範囲の編集・検証・commitと、外部公開としてのpush。
pushの継続承認がある範囲では再確認せず実行し、承認のない公開まで一般化しない。
pushだけが失敗した場合も、実装・ローカル適用・公開のどこまで済んだかを分けて示す。

### 5. 外部Pro相談の開始条件を明示する — 優先度: 中

[use-chatgpt-6-pro](../skills/use-chatgpt-6-pro/SKILL.md)と全体指示は、行き詰まり時の
自発的なPro相談を許容する。これはCodexのsub-agentとは別の仕組みだが、
別モデルへの入力送信と追加利用を伴う。今回のAstra中心の運用では、開始条件を
「ユーザーがPro相談を明示的に指定した場合」に絞る案がある。

これはsub-agent無効化とは別の選好なので今回変更していない。Temporary Chatの
確認、最小限の入力、1回だけの送信、送信成否が不明な場合の再送禁止は残す。

### 6. スキルの説明と重複を整理する — 優先度: 中

個人スキルの `kiss` と `yagni` は短く、明示指定に限定されており、そのままでよい。
[Ponytail](../skills/ponytail/SKILL.md)も必要な検証・互換性・安全性を保持する点はよい。
ただしSessionStart hookは全本文を読み込み、coding以外にもその指示が届く。
全体の簡潔な方針と詳細なモード手順を分け、詳細が必要なときだけ読む改善余地がある。

`add-nix-mcp` と `add-nix-skill` はそれぞれ132行・130行で、共通のホスト確認、
stage、build、commit、test、switchを繰り返す。共通部分をAGENTSへ寄せれば、
ホスト追加時に複数箇所を修正する必要も減る。長さだけを理由に分割せず、
MCPの資格情報・Nixの固定入力・Home Manager配布など固有の要点は本体に残す。

プラグインの説明には次の具体例がある。

- `figma-swiftui` は説明に「iPhone/iPadへの言及で使用」という広い条件を含む。
  USBデバイス操作でも誤って候補になりうるため、FigmaとSwiftUIの変換に限定するとよい。
- `google-docs` の説明は約988文字あり、起動条件に内部実装の手順まで混在する。
  「Google Docsの作成・編集・テンプレート適用」に絞り、コピーやsmart chipなどの
  条件は本文から必要時に参照する形がよい。
- `openai-docs` の「ローカル確認より先に検索」という一律の順序は、このリポジトリの
  最初のホスト確認義務と噛み合わない。環境の安全確認を先に認め、最新仕様が必要な
  問いに公式検索を適用する方が自然。

プラグインやシステムスキルのキャッシュを直接修正すると更新で失われる。
これらは配布元の改善・更新確認の対象とし、個人スキルを重ねて競合を増やさない。

### 7. 検証の停止条件は現在の良い部分を残す — 優先度: 中

AGENTSとPonytailには既に「未変更の入力に対する合格結果を再利用する」方針がある。
ここは維持する。改善対象はdevelopmentとNixスキルに重複する一律のチェック手順。
変更の影響に応じた検証を一箇所で定義し、失敗・追加変更・未解決の懸念がある場合に
再実行する。実システムに影響する場合の `test → health → switch → health` は
重複テストではなく異なる状態の確認なので維持する。

## 推奨する意思決定の境界

| 状況 | 推奨する振る舞い |
| --- | --- |
| 監査・説明だけの依頼 | 調査と助言を完了する。別途指定された設定変更だけ実装する |
| 明示された実装・修正 | 必要な読み込み、編集、失敗修正、適切な検証まで継続する |
| 当リポジトリの変更 | 無関係な変更を保護し、commitする。ローカル適用はAGENTSの影響判定に従う |
| 既に承認された工程 | 同じ承認を再度要求しない |
| 答えで結果・範囲・権限が変わる不明点 | その不明点だけ確認し、独立してできる作業は進める |
| 別ホストへの操作 | そのホストと操作への明示的な許可が必要 |
| 公開・外部送信・破壊的操作 | 既存の承認がその操作を含むかを確認し、含まなければ実行前に確認する |
| sub-agent | 使用しない。別タスクや別エージェントで代用しない |

ホスト一致の確認、無関係な変更の保護、秘密情報をNix storeへ入れない規則、
Orangeの443/loopback構成、ハードウェア操作の座標校正と結果確認は残すべき境界。
「Astraは賢い」という理由だけでは削除しない。

改善後の確認には、誤字修正、個人スキル更新、VM上のCodex設定変更、Orange専用の
宣言変更、iPadのスクリーンショット取得、大きな調査を代表ケースとして使う。
不要なスキル発火・再確認・検証の重複を確認するとともに、必要な適用や安全確認の
抜けがないことを確認する。これらの比較は次の改善を実装した際に行う提案である。
